# 技术栈选型

> 版本：v1.3 · 2026-11-13（对应应用 v0.4.0）
> 适用范围：MotorPulse 大电机温度/电流 LoRa 监测平台试点版

## 1. 结论

| 层级 | 选型 | 版本基线 | 选择理由 |
| :--- | :--- | :--- | :--- |
| 前端框架 | Vue 3 + TypeScript | Vue 3.5 / TS 5.7 | 现有 UI 为原生 HTML/CSS，Vue 模板迁移成本低；TS 保证接口契约 |
| 构建工具 | Vite | 6.x | 启动快、生产构建简单、生态主流 |
| 状态/路由 | Pinia / Vue Router | 2.3 / 4.5 | Vue 官方推荐组合，适合 7 个业务视图（含设备配置与通知机器人） |
| 图表 | Apache ECharts | 5.5 | 双轴趋势、四象限、阈值线、响应式能力成熟 |
| 后端框架 | FastAPI + Pydantic | 0.115 / 2.10 | 类型化、自动 OpenAPI、轻量、适合内部 API |
| ORM / 迁移 | SQLAlchemy + Alembic | 2.0 / 1.14 | 关系模型清晰，迁移可审计；同步 Session 简化低并发事务 |
| 数据库 | PostgreSQL | 16 | 关系主数据 + 时序读数的平衡点；窗口函数、JSON、备份成熟 |
| 采集 | pymodbus | 3.8 | 与现场测试脚本一致，支持 RTU over TCP / Modbus TCP |
| 采集调度 | 内置后台线程 | - | 单网关、15 分钟周期，无需引入 Celery/Redis |
| 通知 | 飞书应用机器人（lark-oapi 长连接）+ Webhook 回退 | 1.7.5 | 卡片按钮回传闭环、图片快照、无需公网回调 |
| 部署 | Docker Compose + Nginx | - | 3 个容器覆盖数据库、API、前端，贴合单厂试点 |
| 认证 | SSO 网关代理（`X-Auth-User`） | - | 符合项目规范“统一身份认证、不建独立账号体系” |
| 代码质量 | pytest / black / flake8 / isort / pre-commit / vue-tsc / ESLint / Prettier | - | 覆盖后端测试、格式、静态检查与前端类型检查 |

## 2. 需求与约束

| 约束 | 现状 | 对架构的影响 |
| :--- | :--- | :--- |
| 采集周期 | 15 分钟/次 | 不需要流式计算、消息队列；定时批处理即可 |
| 采集点位 | 当前 1 个网关，后续多网关；总数 ≤ 100 | 单进程顺序采集可承受；模型需要网关/传感器/电机多对多扩展 |
| 传感器供电 | 市电供电 | 不需要低功耗休眠策略；UI 不展示“电量” |
| LoRa 参数 | 当前记录 470 MHz / 1200 bps | 作为配置展示，不参与采集协议解析；需现场确认“1200”的含义 |
| 网络 | 公司内网，可访问外网 | Docker 拉镜像、飞书开放平台长连接可用；业务数据仍保存在厂内 |
| 并发 | 同时在线 ≤ 10 人 | 单体 API + 单 worker 足够；不需要负载均衡集群 |
| 部署 | Docker | Compose 三容器；配置全部环境变量化 |
| 数据 | 本地保存，不出厂 | PostgreSQL 本地卷；飞书只发送告警摘要与监测快照，不发送全量原始数据 |
| 控制边界 | 只监测、只报警 | 采集链路只读，不实现写寄存器/停机控制 |

## 3. 容量测算

### 3.1 数据量

- 100 个点位 × 96 次/天 = **9,600 行/天**
- 一年约 **350 万行**
- 单行读数（含温度、三相电流、质量、JSON 原始值）按 200 B 估算，一年约 **0.7 GB**，加索引约 **1–1.5 GB**
- 默认保留 180 天，约 **0.4–0.8 GB**

远低于 PostgreSQL 单机舒适区，无需 TimescaleDB/InfluxDB。

### 3.2 采集耗时

- 正常单点 Modbus 读取约 30–100 ms
- 100 点顺序读取约 **3–10 秒**（含 50 ms 间隔）
- 异常时单点最多重试 2 次，超时 3 秒；最坏情况仍远小于 15 分钟
- 多网关时当前按网关顺序执行；按 5 个网关、每网 20 点估算，单轮仍可在 1 分钟内完成

### 3.3 API 并发

- 10 个在线用户，按每人每分钟 2 次请求计算，约 **0.33 QPS**
- 日报/趋势查询按单电机 2,880 行（30 天 × 96）计算，Python 聚合约毫秒级
- 基线计算有 60 分钟缓存，避免每轮采集重复扫描 30 天数据

## 4. 关键选型对比

### 4.1 前端：Vue 3 vs React vs 原生

| 方案 | 优点 | 缺点 | 结论 |
| :--- | :--- | :--- | :--- |
| Vue 3 + TS | 模板贴近现有 HTML/CSS；学习成本低；官方生态完整 | 大型团队生态略小于 React | **采用** |
| React + TS | 生态最大 | 现有静态设计需要整体重写为 JSX，迁移成本更高 | 不采用 |
| 原生 HTML/JS | 无构建链 | 1,200 行单文件不可维护，无类型与组件化 | 仅作为设计参考 |

ECharts 相比 Chart.js 更适合双 Y 轴、阈值线、四象限与密集时间序列；相比 D3 开发效率更高。

### 4.2 后端：FastAPI vs Django vs Flask

| 方案 | 优点 | 缺点 | 结论 |
| :--- | :--- | :--- | :--- |
| FastAPI | 类型化、自动 OpenAPI、依赖注入、性能好 | 需要自己组织项目结构 | **采用** |
| Django | 后台/ORM/权限完整 | 对本项目偏重；后台与现有 UI 重复 | 不采用 |
| Flask | 轻量灵活 | 缺少内建 OpenAPI 与类型校验 | 不采用 |

采用**同步 SQLAlchemy Session** 而不是全异步 ORM：并发极低、事务边界清晰，采集线程与 API 线程共享同一套模型更简单；FastAPI 的同步路由会进入线程池，不会阻塞事件循环。

### 4.3 数据库：PostgreSQL vs SQLite vs 时序库

| 方案 | 适用 | 结论 |
| :--- | :--- | :--- |
| PostgreSQL 16 | 主数据关系、时间范围查询、窗口函数、备份成熟 | **生产采用** |
| SQLite | 零运维、单文件，适合本地开发与自动化测试 | **开发/测试采用** |
| TimescaleDB | 更高采样频率、压缩、连续聚合 | 当前规模不需要；作为演进选项 |
| InfluxDB 等 | 纯时序、高写入 | 主数据关系与分析 SQL 反而变复杂 | 不采用 |

当前用 Python 做分桶聚合（15 分钟/1 小时/6 小时），单电机 30 天仅 2,880 行，简单可靠；若未来点位 > 1,000 或频率提升到分钟级，再引入 TimescaleDB。

### 4.4 采集：内置线程 vs 独立服务 vs Celery

| 方案 | 结论 |
| :--- | :--- |
| API 进程内后台线程 | **采用**：单实例、15 分钟、≤100 点；部署最简单 |
| 独立 collector 容器 | 演进选项：多副本 API 或需要独立扩缩容时拆分 |
| Celery + Redis | 过度设计：任务频率低、无分布式需求，增加运维面 |

采集线程通过 `MP_RUN_COLLECTOR` 控制，只在单副本启用；若未来横向扩容，必须拆分 collector 或只让一个副本运行采集。

### 4.5 通知与认证

- **飞书**：优先使用企业自建应用机器人，通过官方 SDK 长连接订阅 `card.action.trigger`，告警时上传监测快照并发送“已解决/未解决”卡片；Webhook 作为兼容回退。每次发送与回调落 `notification_logs`/`audit_logs`。
- **认证**：不建本地账号体系。生产由公司 SSO/oauth2-proxy 在 Nginx 前完成认证并注入 `X-Auth-User`，后端 `MP_AUTH_MODE=proxy` 校验该头；试点可 `off` 直连内网。该模式满足“统一身份认证”的方向，同时避免在应用内重复实现登录。

## 6. 架构原则

1. **API-first**：前端所有数据来自 REST API，FastAPI 自动输出 OpenAPI。
2. **配置分级**：数据库、Webhook 密钥、采集周期、LoRa 参数、认证模式通过 `MP_*` 环境变量注入；飞书应用 App ID/Secret/Chat ID 由前端写入本地数据库，接口不回传 Secret。
3. **可迁移**：Alembic 管理表结构，部署入口自动执行 `alembic upgrade head`。
4. **可审计**：告警闭环、阈值修改、通知发送均落库；请求带 `X-Request-ID`。
5. **只读边界**：采集只调用 `read_holding_registers`，不存在写寄存器/控制指令路径。
6. **渐进式架构**：当前单体 + 内置采集；未来可按“collector 独立容器 → 消息队列 → TimescaleDB”演进，不提前引入复杂度。

## 7. 风险与待确认项

| 项 | 现状 | 处理 |
| :--- | :--- | :--- |
| LoRa “传输频率 1200” | 需求原文未注明单位 | 当前按 **1200 bps** 记录展示，可通过 `MP_LORA_BAUD_RATE` 修改；请现场确认是串口波特率、空口速率还是其他参数 |
| 电流倍率 | 测试脚本按 0.01 A 示例，手册 OCR 不明确 | 点表 `scale` 可配置；上线前用钳形表/变频器显示值比对 |
| 网关并发连接数 | 未知 | 采集按网关顺序单连接；多网关仍顺序执行，避免网关连接数限制 |
| SSO IdP | 未提供 | 先以 `off` 试点；验收前由信息部门提供 OIDC/oauth2-proxy 接入参数，切换 `proxy` 模式 |
| Docker 构建 | 本机 Docker daemon 未运行 | 已完成 `docker compose config` 校验；需在部署机执行 `docker compose up -d --build` |
| 真实 Modbus 连通性 | 开发机无法访问现场 `10.112.66.231` | 部署到厂区网后执行 `python -m app.cli collect-once` 验证 |
| 飞书机器人 | 未提供真实应用凭据 | 开放平台创建企业自建应用，在前端“通知机器人”页绑定 App ID/Secret/Chat ID 后发送测试消息；长连接需外网访问 `open.feishu.cn` |

## 8. 演进路线

| 阶段 | 触发条件 | 调整 |
| :--- | :--- | :--- |
| 试点（当前） | ≤100 点、单/少网关、10 用户 | Compose + 单 API + 内置采集 |
| 扩展 | 多网关、多车间、API 多副本 | collector 拆独立容器；只允许一个采集实例或按网关分片 |
| 高频 | 采样 ≤1 分钟或点位 >1,000 | 引入 TimescaleDB/连续聚合；批量写入 |
| 平台化 | 需要对接 CMMS/工单/统一告警 | 增加消息队列、Webhook 出站、工单系统适配器 |
| 分析增强 | 已采集三轴速度 RMS；若需要频谱/高频波形 | 独立高频采集链路；当前 15 分钟 LoRa 只适合趋势级振动监测 |
